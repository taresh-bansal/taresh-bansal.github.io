Fault-tolerant ticket booking on Raft

Oct – Nov 2025

Distributed systems · Consensus

Bookings that survive a leader failure and never oversell

A movie-ticket booking system replicated across a three-node cluster with the Raft consensus protocol, so every node agrees on the bookings and the service keeps running when the leader fails. Underneath, a gRPC booking service with per-show locking guarantees that concurrent clients never take the same seat.

Code (booking service)Full Raft implementation available on request

Problem

A booking service on a single server stops when that server fails, and replicas that disagree can sell the same seat twice. Even on one server, clients reserving at the same moment can oversell a show. Bookings need one agreed order across machines and safe updates within each one.

Raft layer

What I built

  • A three-node cluster whose nodes talk over gRPC, with the Raft messages defined in Protocol Buffers.
  • Leader election with randomized election timeouts and RequestVote RPCs.
  • Log replication of bookings from the leader to the followers through AppendEntries, which also serve as heartbeats.
  • Automatic failover: when the leader fails, the remaining nodes elect a new leader and booking continues.
  • Clients routed to the current leader, and an application server that applies bookings from the replicated log.

Booking service

Services

Three gRPC services defined in Protocol Buffers. BookingService lists shows, reports seats, reserves and cancels bookings, and streams seat-availability updates. AdminService adds and updates shows, lists bookings, resets data and launches concurrent-booking simulations. LLMService answers user questions.

Concurrency

Each show has its own re-entrant lock, held while checking availability, decrementing seats and creating the booking, so two clients cannot both take the last seat. Cancellations return seats under the same lock.

Testing

An admin RPC runs many simulated clients at once in a thread pool. Integration tests use it to check that when more clients compete than there are seats, no more bookings are confirmed than seats exist and availability never drops below zero.

Assistant

Common questions are answered from a small FAQ map; other questions go to a local Hugging Face Transformers model (FLAN-T5 small by default), so no external API is needed.

Stack

Python, gRPC, Protocol Buffers, Raft consensus, pytest, Hugging Face Transformers. Command-line clients for users, admins and the assistant.
